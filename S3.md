## S3 details

1. S3 is object storage -> Used when a system needs to access an entire object or file.
2. It is part of the Amazon ecosystem.
3. S3 can be accessed using the console, CLI, SDK, as well as the REST API.
4. There are no directories within S3, and it cannot be mounted to a server. It has a flat file structure.
5. Example storage: Media, Images, Videos, and Audios.
6. Usage: When a website is accessed by the user, the request is sent to the server, which sends an HTML file that consists of a URL that points back to S3. This way, the media will be downloaded directly from S3.
7. Each object uploaded to S3 has some properties associated with it. The name of the file will be the key, and the file data will be the value.
8. If versioning is enabled, a version ID is also associated with it.
9. The data in S3 is going to be replicated across servers and multiple availability zones. This ensures availability in case of failure.
10. S3 bucket names must be unique globally across all AWS accounts.
11. Restrictions:
    1. S3 can handle an unlimited number of objects.
    2. Maximum size of a single file is 5TB.
    3. An AWS account supports 100 buckets by default. This can be increased to 1000 by requesting a service limit increase.
12. Since S3 follows a global namespace, all the regions are checked by default.
13. When a first bucket is created, the region can be specified by the user.
14. By default, public access to the buckets is disabled. It can be enabled by the user as needed.
15. Buckets that are not empty cannot be deleted.

## S3 storage classes
1. S3 Standard
   1. When a file is uploaded to S3 standard, the objects are replicated across at least three availability zones.
   2. This is 11 9's worth of durability. Billing is done gigabyte per month.
   3. The latency is low, so files are available immediately.
   4. The files can be made public.
   5. Uploading data (Ingress) to S3 is not charged. Data transferred out to the public internet or other regions (Egress) is charged per GB.
   6. In S3 Standard, there is no minimum size, retrieval fee (to access or read files), or minimum duration. 
2. S3 Standard -IA
   1. The objects are replicated across at least three availability zones.
   2. This is 11 9's worth of durability.
   3. Billing is done GB per month but is a lot cheaper than S3 Standard.
   4. The latency is low, so files are available immediately.
   5. The files can be made public.
   6. Ingress is free; egress is charged per GB.
   7. There is a retrieval fee.
   8. A minimum fee is applicable for 30 days. Hence, even if the storage is done for less than 30 days, the full 30-day amount should be paid.
   9. A minimum size charge of 128 KB per object is applied.
   10. Use case: Data that is not accessed frequently and that is not small in size.
3. S3 One Zone-IA
   1. Cheaper than S3 Standard and S3 Standard -IA.
   2. No replication across multiple availability zones. But it is replicated within the availability zone. In case the zone goes down, the data can be lost.
   3. The latency is low, so files are available immediately.
   4. The files can be made public.
   5. Ingress is free; egress is charged per GB.
   6. There is a retrieval fee.
   7. A minimum fee is applicable for a duration of 30 days. Hence, even if the storage is done for less than 30 days, the full 30-day amount should be paid.
   8. A minimum size charge of 128 KB per object is applied.
   9. Use case: Data that is not accessed frequently and that is not small in size.
4. S3 Glacier-Instant
   1. Low-cost storage option for data that is rarely accessed. Hence, the fee is a lot lower than the other storage classes.
   2. The latency is low, so files are available immediately.
   3. The objects are replicated across multiple availability zones.
   4. This is 11 9's worth of durability.
   5. Ingress is free; egress is charged per GB.
   6. A minimum fee is applicable for a duration of 90 days.
   7. A minimum size charge of 128 KB per object is applied.
5. S3 Glacier-Flexible
   1. The storage class where objects are not immediately available.
   2. The objects are in a state of sleep and need to wake up from a cold start.
   3. Billing is per GB per month.
   4. When data is retrieved, the fee is applicable according to how fast the data needs to be retrieved, and the per-GB egress charge is applicable.
      1. Expedited -> 2-5 minutes
      2. Standard -> 3-4 hours
      3. Bulk -> 5-12 hours
   5. Minimum duration charge is 90 days, and a minimum size charge is 4 KB per object.
   6. The data, when retrieved, is temporarily stored in the S3 Standard-IA storage class.
6. S3 Glacial Deep Archive
   1. Cheapest storage class in S3.
   2. The objects are in a state of sleep and need to wake up from a cold start. Not publicly accessible either.
   3. Billing is per GB per month.
   4. Egress is per GB charge. No ingress charge. Retrieval fee applicable.
   5. Minimum duration charge is 180 days, and a minimum size charge is 4 KB per object.
   6. Retrieval fees are two types: Standard is 12 hours, and Bulk is 48 hours.
7. S3 Intelligent Tiering
   1. Automatically reduces storage costs by intelligently moving data to the most cost-effective access tier.
   2. Apart from the costs of the storage class the data is moved to, all objects will also incur a monitoring/automation cost per 1000 objects.
 
## AWS CLI (Command Line Interface)
1. List all buckets -> ``` aws s3 ls ```
2. Create new bucket -> ``` aws s3 mb s3://<bucket-name> --region <region-name> ```
3. Delete bucket -> ``` aws rb s3://<bucket-name> ``` (will not delete buckets that contain files) ``` aws rb s3://<bucket-name> --force ``` (to delete buckets with files in them)
4. List objects in Bucket -> ``` aws s3 ls s3://<bucket-name> ```
5. All the objects in all the files -> ``` aws s3 ls s3://<bucket-name> --recursive ```
6. Copy file from local machine to S3 bucket -> ``` aws s3 cp <file-name> s3://<bucket-name> ```
7. Copy file from S3 to local machine -> ``` aws s3 cp s3://<bucket-name>/<file-name> <local-path> ```
8. Copy from one bucket to another -> ``` aws s3 cp s3://<bucket-name>/<file-name> s3://<other-bucket-name> ```
9. Delete Objects -> ```aws s3 rm s3://<bucket-name>/<file-name> ```
10. Copy all the contents of a local folder -> ```aws s3 cp <folder-name>/ s3://<bucket-name> --recursive ```. Similar for bucket to folder or bucket to bucket.
11. Delete a file from the local machine and copy it into the bucket -> ``` aws s3 mv <file-name> s3://<bucket-name> ```. Similar for folder to bucket, bucket to folder or bucket to bucket.
12. The sync command is used to sync only the new and modified files to the Amazon bucket from our directory -> ``` aws sync / s3://<bucket-name> ```
13. Find which region the bucket is in -> ``` aws s3api get-bucket-location --bucket your-bucket-name ```
14. To copy content without downloading the file -> ```aws s3 cp s3://<bucket-name>/<file-name> - ```

## ACLs & Resource Policies
1. The Creator and Root User only have access to the S3 bucket.
2. Resource policy -> Determines who has access to an S3 resource
3. S3 Bucket Policy -> Determines who can have access to the bucket and what operations they can perform.
4. An IAM policy is attached to he users and is only applied to authenticated AWS Users and cannot be applied to anonymous users.
5. A resource policy is attached to a resource (like an object, bucket, etc) so the rules can be added for anonymous/public users.
6. ACLs:
   1. A legacy access control mechanism that predates IAM.
   2. They are inflexible and provide only a limited set of rules and are not recommended anymore.
   3. READ, WRITE, READ_ACP, WRITE_ACP, and FULL_CONTROL.

## Versioning in S3
1. Versioning can only be enabled on the bucket, not on the individual object itself.
2. Three states of versioning:
   1. Unversioned -> Versioning is disabled; this is the default state.
   2. Versioning enabled -> Once this is enabled, it cannot be disabled. Hence, we use suspension as an alternative.
   3. Versioning suspended
3. Once versioning is enabled, S3 is going to give a version ID to a file uploaded with the same key. Every time the same object is uploaded, the number of versions of the object is going to increase.
4. The newest version of the object is the latest or the current version.
5. When versioning is not enabled, the version ID is set to null for each of the objects.
6. Versioning helps with accidental deletion of files.
7. When an object is deleted without specifying a version ID, a delete marker is added. This delete marker is a new version of the object without deleting anything. It just gives the illusion of the object being deleted. The marker hides all the versions of the object.
8. To undo deletion, the marker needs to be deleted.
9. Versioning pricing: If a lot of different versions of large objects are stored in the bucket, the charging is done on the sum of all the file sizes.
10. When versioning is disabled, an object with a name and ID of NULL is replaced by an uploaded file with the same name and ID of NULL that is uploaded.
11. If old versions need to be removed, we have to manually delete them ourselves.
12. MFA delete:
    1. It can be found as an option in the version configuration section.
    2. When any changes need to be made to the versioning state of a bucket, MFA should be done. This will be the same for deleting versions as well.
    3. This feature can only be enabled using the CLI.
   
## Lifecycle policies
1. Used to move the objects from one storage class to another automatically after a predefined set of time.
2. Can be applied globally to a bucket or a group of objects that are defined by a prefix or tag.
3. Can be defined for the latest version as well as previous versions.
4. The movement can take place from higher storage classes to lower (price-wise), not the other way around.
5. The only exception is: We can't go from S3 One Zone-IA to S3 Glacier instance retrieval.
6. For small files, less than 128 KB, the following conditions won't work:
   1. Can't go from S3 standard or S3 standard IA to S3 intelligent-tiering or S3 glacier instant.
   2. Can't go from S3 standard to S3 Standard-IA or S3 One Zone-IA.
7. If a file is uploaded to S3 Standard or S3 Standard-IA, a minimum of 30 days' duration is needed before moving it to S3 Standard-IA or S3 One-Zone-IA.
8. If a file is moved from S3 Standard-IA or S3 One Zone-IA, an additional 30 days are needed to move it to one of the Glacier classes.

## Static hosting (Website)
1. S3 gives the option to access static websites through HTTP.
2. S3 gives the URL through which the website can be accessed.
3. To customize a domain for the website, the bucket must follow a specific format.
4. Pricing:
   1. Storage -> price per GB
   2. Egress -> price per GB
   3. Each request to the site is also charged.
   4. If a custom domain name, not S3 assigned, needs to be used, Route 53(AWS DNS service) can be set up so that the bucket can be named the exact same thing.

## S3 Replication
1. Replication: Saving data automatically from a source bucket to a destination bucket.
2. Reasons for replication:
   1. Ensures data protection
   2. Is a compliance requirement
   3. Helps store data closer to users
   4. Keeps data near their servers
3. Types of replication:
   1. Same region replication: Aggregate logs into a single bucket, live replication between prod and test env.
   2. Cross-region replication: Advantages are minimizing latency, fulfilling compliance requirements, and operational efficiency.
   3. Multi-destination replication: 
4. By default, replication is a one-way process. Bi-directional replication should be configured manually.
5. The advantage of bi-directional replication is that the data is always in sync in case of a failover.
6. Replication Requirements:
   1. Versioning should be enabled on both buckets.
   2. AWS S3 permissions should be configured correctly to replicate.
   3. In case of S3 object lock, it should be provided in both the source and destination buckets.
7. Additional points:
   1. Only objects created after enabling replication will be replicated.
   2. S3 provides an option to create a batch replication job to replicate any previous objects.
   3. Encryption-enabled objects will also be replicated.
   4. Objects in S3 Glacier Flexible Retrieval and S3 Glacier Deep Archive storage classes do not get replicated.
   5. Object metadata and tags will be replicated.
   6. Objects can be moved from one storage class to another after replication.
   7. Only after delete marker replication is enabled is the replication done for them.
   8. If a specific version of an object is deleted on the source bucket, that version will not be deleted on the destination bucket. (protection from malicious or accidental deletions)
8. Permissions to perform replication:
   1. When an IAM role is created on the source bucket, a bucket policy needs to be created on the destination so that the user can access the destination bucket.
9. Replication takes time to be visible on the destination bucket. It's not instant.
10. S3 Replication Time Control (S3 RTC) replicates objects within 15 minutes.

## Encryption
1. Scramble data so that only authorized parties can understand the information.
2. Types of Encryption in S3:
   1. Encryption in Transit -> Already natively taken care of by SSL/TLS
   2. Encryption at Rest (when the objects are in the S3 bucket).
3. Different ways to encrypt data in S3:
   1. Client-Side: Client is responsible for encryption and upload for storage.
   2. Server-Side: Give the object to S3, and S3 will encrypt and store.
4. Encryption methods supported by S3:
   1. Server-Side Encryption with Amazon S3-Managed Keys (SSE-S3)
   2. Server-Side Encryption with Customer-Provided Keys (SSE-C)
   3. Server-Side Encryption with Key Management Service Keys (SSE-KMS)
5. Encryption is on a per-object basis.
6. A default encryption method can be configured on a bucket. If no encryption method is provided, the default can be used.

## Pre-Signed URLs
1. These URLs should have an expiration date and should not be provided for an indefinite amount of time.
2. An expiration date of a maximum of 7 days using an IAM user is provided.
3. If an IAM user does not have access to an S3 bucket, a pre-signed URL can still be generated using that account. But the person with the pre-signed URL will have the same access as the user who generated the URL.
4. It is not about access; it is about sending a request to the S3 bucket as the user.
5. Pre-signed URLs are used for cases where we have multiple people who need to access the contents of the S3 bucket but do not need specific AWS accounts.
6. This way, the bucket or an object stays private while being accessible to people who need it.
7. Example use case: Streaming services like Netflix.
