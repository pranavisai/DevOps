1. With AWS Lambda, bring your own code and run it without provisioning servers.
2. It is a serverless computing service.
3. Automatically scales depending on the amount of user traffic. Pay as you use.
4. No charge when there is no traffic.
5. It natively supports programs written in popular languages, including Python, Java, C#, Node.js, Ruby, Go, or PowerShell.
6. Has runtime API extension that allows other programming languages that are not listed.

## How does Lambda work?
1. It starts with an event coming from another AWS service such as S3 or APi Gateway.
2. The event can also be triggered from a stream of data or queues like SQS or Kinesis Data Streams.
3. Push Model: Another service directly triggers Lambda and tells it to activate when something happens.
   1. Synchronous: Lambda returns a response to the event source. In case of failure, automatic retry by Lambda is not done.
   2. Asynchronous: After Lambda is invoked by a source, the event is placed in a queue, and a response of ACK is returned. Retry is done in case of failure. It is important to provide instructions in the code on how to handle retries.
      1. One-minute wait between the first and second attempt and a two-minute wait between the second and third attempt.
      2. If it still fails, the dead-letter queue is sent to Lambda.
      3. Results can be sent to different destinations based on the success.
4. Pull Model: Information flows through a stream or is put in a queue that Lambda periodically pulls, and it goes into action when certain events are detected.

## Access Permissions
1. To make Lambda work, there are 2 types of security permissions.
   1. Push invocation type: Whatever you use as the push event source needs permission to trigger a Lambda function. These are called invocation permissions.
   2. In case of a pull event, Lambda needs permission to access that service. These are called execution roles. 
2. These permissions are given through an IAM resource policy.
3. As an example: If Lambda is allowed to put images into an S3 bucket, then we will have two policies:
   1. IAM policy: That defines what Lambda is allowed to do to the other services.
   2. Trust policy: Allows Lambda to assume the execution role and perform those actions on the other service. It has an allow effect statement, principal as Lambda Service, and an STS assume role action statement.
  
## Lambda functions
1. We need to include a function handler to make our code work with Lambda.
2. Two objects in the function handler:
   1. Event Object: Gives the event source an opportunity to pass information on to the Lambda function.
   2. Context Object: It is generated by AWS and includes information specific to the runtime environment. It helps the code communicate with the runtime environment within the function.

## Lambda pricing
1. Two parts of Lambda cost:
   1. Number of requests
   2. Gigabit Seconds = amount of time the function runs X amount of memory it uses, measured in seconds.
2. When Lambda starts executing the function in response to an event trigger. The request is charged for.
3. Memory allocations can be from 128 MB to 10,240 MB.
4. The type of CPU processor used has an impact on pricing.
5. Ephemeral storage (temporary data storage that is tied to the life of a running process or container and is deleted when it stops or restarts) adds additional storage capacity and can be sized between 512 MB and 10 GB. The cost is region-specific.
6. Provisioned concurrency (an AWS Lambda feature that pre-initializes a set number of execution environments so your serverless functions respond instantly with double-digit millisecond latency) avoids cold start delays. The cost is region-specific and depends on the type of processor selected.
